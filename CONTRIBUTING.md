# Как вносить изменения в Qorgan

Что такое Qorgan и как его запустить — в [README.md](README.md). Здесь — как работать с кодом.
Репозиторий — монорепозиторий на pnpm workspace:

- `apps/web` — фронтенд на Angular ([README](apps/web/README.md));
- `apps/api` — API и воркер на NestJS ([README](apps/api/README.md)).

## Окружение

Нужны Node 24 (`.nvmrc`), pnpm 11 (`corepack enable`) и Docker.

```bash
pnpm install
make dev-deps                              # Postgres и Redis в Docker
cp apps/api/.env.example apps/api/.env     # заполнить JWT_*
pnpm dev:api                               # API на :3000
pnpm dev:web                               # фронтенд на :4200, /api проксируется на :3000
```

- Фронтенд без бэкенда: `http://localhost:4200/?mock=1` — демо-режим на встроенном мок-бэкенде,
  подходит любой логин.
- Воркеру нужны сканеры в `PATH`, поэтому его проще запускать в Docker:
  `docker compose up --build worker`.
- Весь стек целиком: `make up`, затем `http://localhost:8080`.

## Перед PR

```bash
pnpm lint      # eslint для API
pnpm test      # тесты API и фронтенда
pnpm build     # сборка обоих приложений
pnpm --filter @qorgan/web exec prettier --write "src/app/**/*.{ts,html,scss}"
```

CI на каждый PR запускает линтер, тесты и сборку обоих приложений и собирает все Docker-образы
из чистого репозитория. У фронтенда ESLint нет — форматирование держит Prettier. Сборка
фронтенда следит за бюджетами: начальный бандл до 500 кБ, стили одного компонента до 10 кБ.

Изменения интерфейса проверяйте в браузере в демо-режиме, новые маршруты API — запросами
к запущенному серверу. Юнит-тесты этого не заменяют.

## Ветки, коммиты, PR

- Ветка от `main` с префиксом по смыслу: `feat/…`, `fix/…`, `chore/…`.
- Заголовок коммита — одно предложение на английском о том, что изменилось. Подробности — в теле.
- Изменение контракта API делается одним PR: типы и запросы в `apps/web`, маршруты в `apps/api`
  и мок-бэкенд меняются вместе.
- В описании PR: что сделано, как проверено и что не проверено, есть ли миграция и ломающие
  изменения.
- Репозиторий публичный: не коммитьте секреты, `.env`, адреса серверов и данные пользователей.

## Миграции (`apps/api`)

В разработке схему создаёт `synchronize`, в проде — только миграции (`DB_MIGRATE=true`,
применяются при старте API). Поэтому после любого изменения сущностей нужна миграция.
Команды — из `apps/api`:

1. Поднимите пустую базу и приведите её к схеме предыдущей версии:
   `pnpm build && pnpm migration:run`.
2. Сгенерируйте разницу: `pnpm migration:generate src/migrations/<Name>`.
3. Прочитайте результат. Перенос данных, значения для новых обязательных колонок и порядок
   шагов дописываются вручную.
4. Проверьте на базе с данными: `migration:run`, затем `pnpm typeorm migration:revert`
   и снова `run`.

Файлы сущностей должны называться `*.entity.ts` — по этому шаблону их находит CLI.
Не генерируйте миграцию на рабочей базе, в которой `synchronize` уже создал новые таблицы:
разница окажется пустой.

## Соглашения: `apps/api`

**Структура**

- Один домен — одна папка `src/domains/<домен>/` с плоскими файлами: `*.module.ts`,
  `*.controller.ts`, `*.service.ts`, `*.entity.ts`, `dto/*.ts`.
- API (`src/main.ts`) и воркер (`src/worker.ts`) — два процесса из одного кода. Клонирование
  репозиториев, сканеры и вызовы модели выполняются только в воркере.
- Циклических зависимостей между модулями не заводим: `agent` зависит от `spaces`, не наоборот.

**HTTP**

- Все маршруты закрыты глобальным `AccessTokenGuard`; открытые помечаются `@Public()`.
  Пользователь — через `@CurrentUser()`.
- Тело и query — DTO с `class-validator`; id в пути — `ParseUUIDPipe`.
- Доступ проверяется в запросе к базе, по цепочке пользователь → установка GitHub → репозиторий
  (`RepositoriesService.findOwned`, `findManyOwned`, `SpacesService.findOwned`).
- Чужой или несуществующий объект — всегда `404`, а не `403`: не раскрываем, что он существует.
- Сообщения об ошибках для клиента — на английском.

**База**

- Связи с репозиторием — с `onDelete: 'CASCADE'`: синхронизация установки GitHub удаляет
  репозитории жёстко.
- Методы без проверки владельца (`findById`, `findWithInstallation`) — только для воркера.

**Агент**

- Код репозитория, описания PR и вывод модели — недоверенные данные. Доступ к файлам — только
  через `Workspace`; имя репозитория от модели принимается только из списка пространства.
- Код не уходит в модель без предварительного поиска секретов; найденные значения маскируются.
- Агент не меняет CI-конфигурацию, не пишет в default-ветку и ничего не мержит.
- Входы инструментов описываются схемой `zod`; ошибка для модели — `ToolInputError`.
- Каждый запуск записывается через `AgentRunsService` и ограничен бюджетом токенов:
  репозитория — для триажа, фиксов и ревью, пространства — для чата и карты связей.
- Внешние команды — только через `runTool` и `git()` из `domains/scanner`: без shell,
  с таймаутом, токен не попадает в аргументы и URL.
- Новая переменная окружения добавляется в `.env.example` в корне и в `apps/api`.

**Тесты** — Jest, `*.spec.ts` рядом с кодом. Тестов с базой нет: логику выносите в чистые
функции (пример — `domains/spaces/graph/`). Модель подменяется `FakeProvider`, работа с файлами
тестируется на временных каталогах, разбор вывода сканеров — на фикстурах из
`domains/scanner/__fixtures__`.

## Соглашения: `apps/web`

**Angular**

- Только standalone-компоненты с `ChangeDetectionStrategy.OnPush` и `inject()`. Без NgModule.
- Состояние — на сигналах: `signal`, `computed`, `effect`, `input()`, `output()`, `model()`.
  Декораторы `@Input`/`@Output` не используем. RxJS — только для HTTP.
- В шаблонах — `@if` / `@for` / `@switch`.
- Если `effect` вызывает код, который сам читает сигналы, оборачивайте вызов в `untracked`,
  иначе эффект зациклится (пример — `features/shell/shell.ts`).

**Данные**

- `core/api/api.types.ts` — типы, зеркало сущностей API. `core/api/qorgan-api.ts` — все
  HTTP-запросы; в компонентах `HttpClient` не используем.
- Новый запрос — это три правки: тип, метод в `QorganApi` и обработчик в
  `core/mock/mock-backend.ts`. Без третьей сломается демо-режим.
- `core/state/` — общее состояние: `SpaceContext` (выбранное пространство), `RepoContext`
  (выбранный репозиторий пространства), `ScanSession`, `Toasts`.
- Ответ на запрос может прийти после того, как пользователь переключил пространство или
  репозиторий. Перед записью результата проверяйте, что выбор не изменился.

**Интерфейс**

- UI-библиотек нет: SCSS и CSS-переменные из `src/styles.scss`. Цвета берите из переменных —
  так работают обе темы.
- Готовые классы: `.glass`, `.btn`, `.btn-primary`, `.btn-ghost`, `.btn-sm`, `.field`, `.input`,
  `.muted`, `.faint`, `.sr-only`. Иконки — из `shared/icon.ts`, модальные окна — `shared/dialog.ts`.
- Цвета критичности (`--sev-*`) — только для критичности и всегда с подписью, не одним цветом.
- Ответы агента выводим через `MarkdownView`; `innerHTML` не используем.
- У кнопок-иконок должен быть текст для скринридера (`<span class="sr-only">`).

**Тесты** — Vitest, `*.spec.ts` рядом с кодом. Сервисы состояния тестируются с подменённым
`QorganApi` (пример — `core/state/space-context.spec.ts`). Изменили мок-бэкенд — добавьте
случай в `core/mock/mock-backend.spec.ts`.

## Язык

Тексты интерфейса, сообщения API, названия тестов и коммиты — на английском. Комментарии
в коде и документация — на русском. Комментарий нужен там, где без него непонятно, почему
сделано именно так.
